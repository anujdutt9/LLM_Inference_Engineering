The problem

Agents send many more calls than chat users, and each call resends the conversation so far

The question

When there is more work than the GPU can do at once, where does the waiting happen, and who pays for it?

  • Capacity: does a second replica on the same GPU add capacity?
  • Batching: one big engine or two small ones?
  • Placement: which replica should get a call?
  • Overload: queue, refuse, or let vLLM absorb it?
  • Failure: what happens when a replica dies?
  • Memory: what happens when the KV cache is too small?
Why agents are different. A chat request is one call and a person waiting. An agent team is a lead that starts four to eight subagents at once. Every turn resends the history, so prompts grow to 35K tokens, mostly the same prefix. And a refused call doesn't go away; it comes back as a retry. So my question: when there's more work than the GPU can do, where does the waiting happen, and who pays?

Why: Two properties drive everything later: long, mostly repeated prompts (so the prefix cache matters), and refused work that comes back.
How serving works

How vLLM serves one call: wait for a slot, prefill the prompt, then decode one token per step

Slots

+

max-num-seqs = 8: an engine decodes at most 8 calls per step. The 9th waits inside vLLM, where the gateway can't see it.

KV cache and prefix cache

Each running call keeps its prompt's keys and values in GPU memory, in fixed-size blocks. A new prompt that starts with the same blocks reuses them and skips that part of prefill.

Preemption

When the KV pool is full, vLLM drops a running call's KV and recomputes it later. The call still gets its answer, but late.

P/D split

→ KV →

Prefill on one engine, decode on another. The KV moves between them, which only pays if moving it is faster than recomputing it.

vLLM v0.30.0 scheduler · numbers from the Memory bandwidth slide and the KV hand-off baseline (c12)
Some background every result depends on. A call to vLLM waits for a free slot. Prefill reads the whole prompt in one pass and writes its KV cache. Then decode makes one token per step. TTFT is wait plus prefill; the token gap is one decode step. Prefill is limited by compute; decode by memory bandwidth, because every step reads all the weights. An engine has eight slots. Repeated prompt starts reuse cached blocks. When KV memory runs out, vLLM preempts a call and recomputes it. And P/D splits prefill and decode across two engines.

How results are judged

How I judge a run: calls on time, goodput, and the knee where a setup breaks

On time

A call that met every target for its class. Questions load: interactive first token ≤ 2 s, batch ≤ 30 s. Agents: per-role targets from their solo runs.

Goodput

On-time calls per second. Past 8 users this replica served more calls (2.78 /s) but fewer on time: goodput peaked at 2.24 /s and fell.

Knee

The highest step where ≥ 90% of calls are on time: 8 users, exactly the 8 slots. The 9th user waits, and TTFT jumps from 0.07 s to 1.8 s.

When a change counts

> 15% better than its baseline (repeat runs varied ±5%), against a prediction written before the run. S₂ = whole-GPU tokens/s with two replicas ÷ with one.

Why these models

The 27B is strong at SQL and code; the 9B is ~3× cheaper per token and good enough for reading. Same family, tokenizer and parsers, so one gateway serves both.

Why an H100 SXM

80 GB HBM3 at 3.35 TB/s (decode speed depends on it) and FP8 tensor cores (the 27B's weights and our KV cache are FP8). One card, $4.29/h.

Why HAMi, not MIG

HAMi caps each pod's memory at any size while compute stays shared. MIG would give fixed halves, so one engine could never use the whole GPU.

I chose the 27B for reasoning-heavy work: leads, SQL and coding. The 9B is for extraction-heavy readers. Both are hybrid models where only one layer in four uses attention, which sharply reduces KV memory. The 27B's weights are FP8, the 9B's are BF16, and HAMi lets both occupy custom memory slices on the same H100.

Four coding sessions created up to twenty agents for eight slots on the 27B. Full mode cut TTFT p95 from 17.3 to 7.5 seconds and improved every served-call metric. But it refused 140 calls; fourteen coder agents exhausted their retries, and mean session time increased 47 percent, from 7.6 to 11.2 minutes. Refusing an agent's next step delayed or restarted the work rather than removing it. The replay counted 81 refused calls coming straight back as retries within a minute.

Why: Admission was designed for chat. A refused agent call comes back after Retry-After, so refusals add round trips instead of removing load.

Fix: Proposed, not yet tested: session-aware admission. Calls from running sessions wait in the queue; only new sessions are refused. More compute (a second 27B) would also help, but one H100 doesn't have it.

Break-even

214.5 MiB ÷ 0.37 s recompute ≈ 580 MiB/s

Slower link: recomputing on b wins. Go rule: ≤ 5% recomputed on b, identical answer.

docs/presentation/diagrams/pd_intro.png · docs/experiments/c12.md · prefill-log.txt KV Transfer metrics
The last serving question: splitting prefill and decode. On one engine, a 10,000-token prefill stalls every running call's next token. With prefill-decode separation, replica A only prefills, ships the KV cache to replica B, and B decodes. One filing's KV is 13 blocks, 214.5 MiB, which matches vLLM's log. Recomputing it on B takes 0.37 seconds, so the link must move about 580 MiB per second to win.

Why: Whole blocks move, so the last block's empty part travels too: pure KV would be 9,813 × 16 KiB = 153 MiB plus 49 MiB of DeltaNet state.

I tried two transfer libraries, both over TCP; this machine has no RDMA. Both worked: decode recomputed just one token. NIXL wanted GPU-to-GPU copies, which HAMi's separate containers cannot share, so it fell back to 92 MB per second: 2.3 seconds, six times slower than recomputing. Mooncake on the same TCP reached 1,319 MB per second: 0.27 seconds, 25 percent faster. P/D pays only when moving the KV is cheaper than recomputing it.

Why: UCX prefers CUDA IPC, but two HAMi-isolated containers can't share GPU memory handles, so NIXL fell back to slow TCP. Mooncake's one differing answer (3 words) is likely numerical variation from different batching; not isolated, so by the strict rule it's a no-go.

Fix: A fast path: NVLink or RDMA (~47 GiB/s would move it in ~5 ms), CUDA IPC across containers, or Mooncake. Only split P/D when the move beats the recompute.

Appendix · Memory · the loop

Why admission locked itself out: an estimator that only learns from calls it admits

  • 1 · KV full: vLLM preempts and recomputes calls.
  • 2 · The gateway measures those delays as prefill: learned rate 19K → 2,670 tok/s.
  • 3 · Switching to full mode resets vLLM's cache, not the gateway's learned rate.
  • 4 · Estimated TTFT for a 10K document = 10K ÷ 2,670 ≈ 3.7 s → 1.86× of the 1.5× limit → 429.
  • 5 · Nothing admitted, so no new measurement: every call refused, even at KV 0%.
An estimator that learns only from what it admits can lock itself out.
